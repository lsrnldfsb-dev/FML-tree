Feasibility read & build plan

Match Monsters for Two

A private, full-fidelity rebuild of Plato’s shared-board monster battler, for exactly two players who know each other.

Four water → +1 move

Yes, this is buildable — and it is buildable specifically because there are only two of you. Matchmaking, ranked ladders, account recovery, anti-cheat, moderation, monetisation and scaling are the expensive parts of a game like this, and every one of them disappears when the player list is a fixed pair who trust each other. The game is turn-based, so network latency is irrelevant too.

What’s actually left is a deterministic board simulation and a thin server. The simulation is the interesting engineering. The server is a weekend.

Read this part first

The source document is incomplete

You asked for a full clone, so the honest thing to say up front is that the design document we have doesn’t describe a complete game. It stops mid-sentence in the patch-history section, and the roster has real holes in it. A “full clone” therefore means implementing everything specified, and designing the rest ourselves. That’s fine, but it should be a decision rather than a surprise.

  • Roughly twenty monsters don’t exist yet. IDs run to 064, but 031–045, 047–050 and 053–056 are absent. Forty-four monsters are described; the rest are empty slots we’d have to invent.
  • Five named evolutions have no stats at all. Rexsaur, Voidevour, Frostoyle, Purrtea and Crescemoth are referenced as evolution targets and then never specified.
  • Several described abilities are missing numbers. Gargice’s Frostbite has no damage value. Lunarva’s mana cost is literally “Variable” and its crystal mechanic exists only as prose. Aromaphant is listed as a fully-evolved “+” skill with no base form.
  • Whole systems are named but never defined. Stage hazards (only “Lava Caverns” is mentioned), the anomaly-effect rotation, and the monster rarity tiers that Timingo and Flambagant are tagged with.
  • Resolution order is unspecified. When a single cascade both completes a four-tile match and fills a mana bar, which resolves first? The document never says, and the answer materially changes how the game plays.

The loop hazard

Tile-converting abilities can feed themselves. Pelijet turns three tiles into water, which can complete a water match, which refills Pelijet’s bar, which converts three more tiles. The document celebrates this as the dominant strategy without saying where it stops. The engine needs a hard cascade-depth cap and a rule that ability-created matches don’t refund moves — otherwise a single turn can run forever.

My recommendation: build every specified monster first, tune those against real games between the two of you, and treat the blank slots as a design collaboration later. You’ll have much better instincts about what the roster is missing after fifty matches than either of us has now.

Architecture

One pure engine, two dumb clients

The single most important structural decision is that all game logic lives in a pure TypeScript package with no dependencies, no I/O, and no notion of a network. It exposes essentially one function:

applyMove(state, move) → { state, events[] }

Randomness comes from a seed and a counter stored inside the state, so every draw is reproducible. A whole match replays exactly from its seed plus its move log, which means a bug report is just a match ID, and the test suite can assert precise board states rather than vague outcomes.

The events array is the animation script — tiles matched, tiles fell, mana gained, ability fired, damage dealt. The browser never computes game state; it plays back events. A rendering bug therefore cannot desynchronise the match, which is the failure mode that makes homebrew multiplayer games miserable.

packages/engine     pure TS, zero deps — board, cascades, effect DSL, seeded RNG
packages/shared     types, wire protocol, monster + stage data
apps/server         Fastify + ws + SQLite — authoritative state, two accounts
apps/web            React + Vite PWA — renders events, installs to your phones
tools/sprites       prompt set, generation driver, background strip, atlas build

The server holds match state in SQLite and pushes updates over a WebSocket. This gives you live play and asynchronous play from the same code with no fork in the design: if you’re both connected, moves appear instantly; if she’s not, the state sits in the database and a web push notification tells her it’s her turn. Half-played matches survive server restarts and reboots of your VPS.

Authentication is two passphrases and a signed cookie. No email, no reset flow, no OAuth, no password rules. It is about thirty lines, and for a two-person game behind a domain only you two know, it is entirely sufficient.

Move resolution, in a fixed order

Validate the swapAdjacent tiles only, and the swap must complete a line of three or more. Illegal swaps are rejected without consuming a move.
Find every matchScan rows and columns. Award mana to the matching player’s monster of that element, or berries for berry tiles. Matches of an element nobody on your team uses clear for nothing.
Apply match-size bonusesFour tiles refunds a move; five adds a five-point heal; six or more adds five damage. Capped at one extra move per turn when match bonuses are switched off.
Remove, drop, refillGravity pulls tiles down, new tiles enter from the top using the seeded generator so both clients see identical refills.
Rescan for cascadesLoop back to step two, tracking depth. Hard cap prevents converter abilities from looping indefinitely.
Fire filled abilitiesOnce the board settles, any monster at full mana triggers in a fixed slot order and resets to zero. Ability-created matches resolve but grant no further moves.

The content problem

Sixty abilities, twenty-two primitives

Writing sixty monsters as sixty pieces of bespoke code would be unmaintainable, and you’d never be able to rebalance them. Instead each monster is a data entry that composes small typed effects:

{ id: "bonzumi", element: "fire", mana: 8, effects: [ damage(20), clearColumn(1) ] }

Around twenty-two primitives — damage, heal, heal-over-time, clear row, clear column, clear grid, convert tiles, spawn tiles, drain mana, grant mana, steal, modify moves, shield, lock, crack, collect, damage-per-flagged-tile and a handful more — cover almost the entire documented roster. Adding a monster becomes a config change you can make from an admin page without a redeploy, which matters enormously when there are only two of you and no way to playtest at scale.

The interesting ones are the monsters that aren’t one-shot effects. These need persistent per-monster state and event hooks, and they’re the reason the engine is designed the way it is:

Monster The awkward part What the engine needs
GargiceWater Flips between two stances at every turn end; one doubles damage, the other doubles mana gain. Per-monster state plus an onTurnEnd hook, and multipliers applied at damage and mana resolution rather than baked into the effect.
CactkidEarth Spawns bullet tiles, remembers how many you’ve picked up, then pays out per bullet at full mana. A tile-flag layer independent of element, an onTileCollected hook, and a capped counter.
KitteaPsychic Four completely different effects depending on a tea-charge counter from one to ten. Counter state plus threshold branching inside the effect list.
AromaphantPsychic Its effect changes based on the colour of your most recent match. Board history feeding back into the resolver — lastMatchElement tracked on player state.
VoltshardElectric A shield that absorbs five damage per charge, reflects ten per unspent charge, and decays one per turn. An onDamageTaken hook that can both reduce incoming damage and emit new damage back at the attacker.
PetirexFire Cracks tiles now, collects them for damage later. Tile flags again, plus a damage-per-flagged-tile primitive.
EchomoriElectric Drops echo tiles at every turn end and harvests them for damage. Turn-end spawning with a board-saturation limit the document doesn’t define.
AbyssoulWater Gains mana from your other monster’s matches. An onAllyMatch hook, and a decision about whether the bonus stacks with normal gain.
LunarvaPsychic “Alters mana flow based on the active channeled crystal.” No cost, no numbers, no crystal list. Not implementable as written. This one needs a design pass before it can be built at all.

Everything in that table except Lunarva is straightforwardly expressible once the engine supports per-monster state and five lifecycle hooks. That’s the finding that makes a full clone tractable rather than a slog: the roster is large, but it isn’t sixty unique problems.

Build order

Playable early, complete later

These are strictly sequential — each one depends on the last. The important thing about this ordering is that you and your wife are playing real matches against each other at the end of the second phase, long before the roster is finished.

P0
Built

Engine and a hot-seat prototype Done

Board, matching, gravity, cascades, mana, berries, evolution, boost, match-size bonuses, four monsters. Runs entirely in one browser tab with no server. The point is to find out whether the shared-board loop is actually fun before building anything around it.

Done when two people can play a complete match to a win on one screen.

Outcome Engine shipped with 32 monsters and 48 tests, including 40 randomised full playthroughs. Ran wider than planned because the effect DSL made roster entries nearly free. Verified in a real browser: abilities firing, berries accumulating, Turtlelisk evolving into Karaggon.

P1
Small

Online, on your VPS

Server, WebSocket, SQLite persistence, the two-passphrase login, deploy scripts and TLS. Live and asynchronous play both work from here on. This is the milestone that matters most — everything after it is additive, and you can keep playing while I build it.

Done when you two finish a match from separate devices, and a half-played match survives a server restart.

P2
Largest

The full documented roster

The effect DSL fleshed out, all five lifecycle hooks, per-monster state, tile flags, and every one of the forty-four specified monsters with their evolutions. Plus an admin page for editing damage, mana costs and thresholds live.

Done when every monster in the document is playable and you can retune any number without a redeploy.

P3
Medium

Modes, notifications, polish

Draft mode with elemental ban lockout, All Pick with its unique-element rule, stage voting with the coin-flip tiebreak, the plus-five health compensation, the match-bonus toggle. Then phone push notifications for your turn, animation timing, sound, and match replays.

Done when the whole pre-game flow matches the document and her phone buzzes when it’s her move.

P4
Open-ended

Sprites and the missing content

Generated monster art swapped in over the placeholders, the twenty invented roster slots, the five unspecified evolutions, stage hazards, the anomaly rotation, skins. This phase never really finishes, which is the point — it’s where the game keeps growing after it’s already good.

Done when you stop wanting new monsters, which I suspect is never.

Honest risks

What could go wrong

  • Balance is genuinely untestable with two players. The numbers in the document come from a live game with thousands of matches behind them, and some of them will feel wrong in your household. This is why the admin tuning page is in P2 rather than treated as a nicety — you need to be able to nerf something the evening it annoys you.
  • The exotic monsters are where bugs will live. Stances, token counters, reflect shields and conditional effects interact in ways nobody has enumerated. Mitigated by the engine being pure and deterministic: every ability gets unit tests asserting exact board and health states, and any weird match can be replayed from its seed.
  • P2 is much bigger than it looks. Forty-four monsters with real abilities is the bulk of the whole project. It’s sequenced after you’re already playing precisely so its length doesn’t block your fun.
  • I can’t generate the sprites from here. This environment has no image-generation tool. I can write the prompt set, the style guide and the whole processing pipeline, but the actual pixels need either an API key placed on your server or you running the prompts yourself. Details below.
  • Keep it private. Rebuilding someone else’s game design for two people in one household is a non-issue. If it ever went public, the monster names and any art resembling theirs would be the problem, not the mechanics — worth knowing now so we can pick names accordingly.

Which service or tool do you have access to? If you have an API key, put it in an environment file on the server rather than pasting it into chat, and I’ll write a script that drives it. Otherwise I’ll produce a numbered prompt sheet and a style guide, you generate in batches, and I’ll handle background removal, cropping and atlas packing from whatever you drop in.

Names

Keep Bonzumi, Pelijet, Turtlelisk and the rest, or rename the roster as we go? Both are fine for private use. Renaming costs nothing now and quite a lot later, so it’s worth deciding before P2.

Two small rulings

Should a cascade that a monster’s ability caused be able to refund moves? I recommend no, or converter monsters run away with the game. And when a four-tile match and a full mana bar land in the same cascade, I’ll resolve the move refund first and the ability after the board settles — say if you’d rather it went the other way.
